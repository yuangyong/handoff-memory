# Handoff Memory 的价值与恢复方式对照

## 它解决什么问题

新 AI 会话当然可以重新扫描整个项目，但这种方式需要临时决定读哪些文件、相信哪些描述、运行哪些检查。扫描范围不足会遗漏关键背景，范围过大又会重复消耗时间和上下文。

Handoff Memory 提供的是一个确定、可审计的恢复入口：旧会话先把持续目标、已完成结果、关键决策、产物、验证依据、风险和下一步提炼到本地交接；新会话通过 `hmem resume` 同时取得交接正文、保存时间、正文一致性和当前 Git/SVN 状态。交接负责定位任务，当前产物与证据负责确认事实。

## 两种恢复方式的对比

| 维度 | `session-handoff` 恢复 | 子智能体独立读取 |
|---|---|---|
| 恢复速度 | 快，一条命令获得完整上下文 | 慢，需要搜索文件、Git、安装环境和测试 |
| 确定性 | 高，使用固定流程和稳定 JSON Schema | 取决于子智能体选择了哪些证据 |
| 完整性校验 | 自动检查正文哈希、状态漂移和敏感信息 | 必须自行建立比较基线并完成检查 |
| 安全性 | 恢复只读，明确禁止自动执行旧命令 | 依赖提示约束和智能体的临场判断 |
| 深度取证 | 中等，主要恢复已保存的上下文与证据 | 强，可以重新检查实现、产物并运行测试 |
| 可追溯性 | 有快照、时间、提交和哈希，但不依赖客户端会话 ID | 能给出更丰富的取证过程，但结果不够稳定 |
| 上下文成本 | 低，先读精炼交接，再定向补证 | 较高，容易重复读取文件和运行测试 |

> **结论：** 日常跨会话接续应优先使用 `session-handoff` 建立可信起点；发布、数据完整性、并发安全等高风险任务，再追加独立取证。

如果只能选择一种方式，CLI 辅助恢复更适合作为默认方案。跨会话工具最重要的不是重新“猜测上次做了什么”，而是确定读到哪份交接、交接是否变化、项目状态是否漂移，以及哪些事实仍需复核。子智能体独立读取更适合作为二次审计：它能发现最新环境中的新问题，但不应成为每次恢复都要重复执行的前置成本。

## 一次项目内对照验证

本项目曾使用同一份交接进行两路只读恢复：一路运行 `hmem resume . --format json`，另一路让独立子智能体直接读取历史快照并检查仓库。

CLI 路径立即确认了以下事实：

- `ACTIVE.md` 与最近保存正文的 SHA-256 一致；
- 当前分支、提交、工作区和保存时相比没有漂移；
- 恢复结果没有格式、安全或质量警告；
- 恢复前后的 `.ai-memory` 文件保持不变。

独立取证补充检查了提交内容、安装入口和测试，并在一次完整测试中遇到 Windows 并发锁测试的间歇性失败；之后针对该测试连续复跑 3 次和 20 次均通过。这个差异说明：交接中的“测试通过”是保存时的验证记录，新会话仍应根据任务风险判断是否需要重新验证。CLI 负责可靠恢复上下文，智能体负责验证当前世界，两者结合比单独使用任何一种方式更稳健。

这是一项项目内验证，不是跨模型性能基准；它用于说明恢复职责和证据边界，不用于比较模型能力。

## 推荐恢复流程

```text
用户明确要求恢复或继续任务
  └─ session-handoff 调用 hmem resume
       ├─ 核对保存时间、正文一致性、安全提示和仓库漂移
       ├─ 区分“当前已核验”与“交接记录但本次尚未核验”
       ├─ 仅对时间敏感或高风险声明追加取证
       └─ 从交接中的第一个可执行步骤继续
```

推荐让新会话先执行：

> 请使用 session-handoff 技能恢复上一次任务，先区分当前已核验事实和交接中尚未复核的记录，再继续下一步。

## 能力边界

- 它不是聊天记录器，不保存“模型记住的一切”。
- 它不是事实数据库；交接是恢复索引，当前产物、来源、人工确认、版本库和测试才是事实源。
- 它不自动执行交接中的命令，也不因普通任务完成或对话结束而自动保存。
- 它不依赖某个 AI 客户端的私有会话 ID；跨工具接续依靠项目内快照、正文摘要和版本库状态。
- 它不能恢复未曾显式保存的对话进展；意外关闭后只能使用最近一次快照和当前项目状态继续。
